# Jira embedded Light House context

Proposed read-only Sprint 5 integration, researched 2026-11-28. This document does not register a module, implement a resolver, change scopes or establish hosted acceptance. Forge MCP was unavailable; exact official documentation was consulted directly.

## Supported surface and context boundary

Use a static `jira:issueContext` Custom UI resource with a dedicated resolver. The documented module is not labelled Preview, supports Jira and JSM, and renders a collapsible panel in the new issue view. The older `jira:issueGlance` is deprecated in favour of issue context. Avoid adding dynamic registration or a background script for this single panel. [Issue context](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-issue-context/), [Issue glance deprecation](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-issue-glance/).

The app-context security guide guarantees resolver context for authorisation and explicitly excludes browser Bridge `getContext`. However, the resolver reference also warns that not every context value is guaranteed and that extension context is module-specific, not a one-to-one platform-context mapping. Therefore do not claim that `extension.issue.id` alone authorises reading SQL. Treat the actual server-supplied issue/project identifiers as validated candidates, never accept replacements from the payload, and independently verify current Jira access and durable tenant membership. Missing or unsupported server context fails closed. [Context security](https://developer.atlassian.com/platform/forge/app-context-security/), [Resolver context contract](https://developer.atlassian.com/platform/forge/runtime-reference/forge-resolver/).

## Minimal proposed request and lookup

1. UI invokes `embeddedIncident` with exactly `{action: "read"}`. Reject unknown keys, including client installation, account, tenant, incident, issue or project selectors. Derive installation/environment using the existing trusted `getAppContext` boundary, require DEVELOPMENT while that remains the application restriction, and derive the signed-in account from resolver context. Require the expected module context; reject absent/anonymous identity. Bridge context is display-only.
2. Validate numeric issue/project candidates from the resolver extension. In the current interactive resolver, call `api.asUser().requestJira(route\`/rest/api/3/issue/${issueId}?fields=project\`)`with GET. Validate returned issue ID and project ID against candidates. Do not resolve by issue key, request expansions, update history, or fall back to`asApp`/offline impersonation. Mask inaccessible/missing issues with a fixed unavailable result. This read independently enforces Browse projects and issue-level security. The endpoint recommends `read:jira-work`, already present in the local manifest; native consent and current permissions remain unverified. [Get issue](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-get), [Forge requestJira](https://developer.atlassian.com/platform/forge/apis-reference/fetch-api-product.requestjira/).
3. Add a narrow repository port `linkedIncident(installationId, issueId)` returning at most one internal `{tenantId,incidentId,projectId}`. Read only `jsm_intents.state = linked` with exact installation and issue ID. Verify immutable configuration project equals the freshly read Jira project. The existing v004 unique installation/issue constraint supports this lookup; the current `JsmRepository` port has no reverse lookup, so this is proposed additive work. No marker search, key-based inference or tenant ownership from client input.
4. Construct the existing inventory service using server installation/account, call `context(mappedTenantId, 'read')` for fresh membership/expiry checks, and enforce active tenant with no pending mutation. Load incident and optional operations under that trusted tenant context. Reject mismatched/ambiguous mappings or foreign records before projection. Jira access never grants Light House tenant access, and tenant access never grants Jira issue access.
5. Return a small public DTO: issue ID/key, incident ID, creation state, separate current operational state/version, SLA priority/warning/deadline, impact counts, owner team/assignee references and pending-operation booleans. Missing operational schema is explicitly unavailable, not a fabricated state. Exclude installation/account IDs, secrets, request/configuration snapshots, markers, lease tokens and raw pending audit. Do not expose tenant lookup details on denial.

## UI and acceptance prerequisites

Show loading, linked summary, unlinked issue, unavailable and retry states; refresh explicitly and after relevant issue changes with bounded calls. Opening a workspace reauthorises through its existing resolver. This panel does not create tickets, initialise operations, migrate, provision sources or transition/close issues. Display conditions are presentation only.

Before implementation: agree the reverse-lookup port/projection, confirm the installed SDK's actual resolver extension shape, and review the new manifest resource/module. Local negative tests must cover altered payloads, missing/foreign contexts, changed Jira access/project, revoked/expired tenant grants, pending parent, absent/ambiguous links, and private-field exclusion. Any deployment/installation change and native issue-view acceptance require separate applicable authority and fresh resource/prerequisite reconciliation. No native result or new permission approval is implied here.

## Module-key evidence limit

The official AppContext API defines `moduleKey` as a manifest module key, without specifying whether a Custom UI resolver receives its invoking UI module key or the function module key. The installed `@forge/api` 8.5.1 implementation (`out/api/runtime.js`, `getAppContext`) forwards `runtime.appContext.moduleKey` unchanged. The installed `@forge/resolver` 2.0.2 forwards contextual fields and replaces account identity from the backend principal, but does not normalise module keys. Its documented context type does not explicitly promise a `moduleKey` property. These sources do not prove either key interpretation. [AppContext API](https://developer.atlassian.com/platform/forge/runtime-reference/app-context-api/).

Use a dedicated read-only resolver entrypoint, the expected server extension type, and the independent Jira/tenant checks above. Do not introduce an assumed `context.moduleKey` requirement or a wildcard fallback. If the implementation additionally checks runtime module keys before native verification, an explicit finite compatibility policy accepting only the exact issue-context key or its dedicated resolver-function key must be labelled provisional. Neither acceptance proves the invoking UI identity, and browser keys must never satisfy the check. Verify the actual runtime shape with safe allowlisted evidence during a separately authorised hosted session before claiming module-key binding acceptance.

## Scope review correction

The proposed interactive read needs no additional user-profile call. GET `/rest/api/3/myself` requires `read:jira-user` (or its documented granular alternatives), which the current manifest does not contain. Both the embedded issue verifier and the independent transition gateway must rely on the trusted resolver principal and resolver-bound `api.asUser()` instead of adding that redundant call or requesting broader scopes. Plan/session account binding remains mandatory at the application boundary; these adapters must never run queued, impersonate another account or fall back to `asApp`. GET issue and transition availability retain their independent issue/project/permission checks. [Get current user scopes](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-myself/#api-rest-api-3-myself-get).

## Implemented local integration — 2026-11-28

The read-only application lookup/SQL repository, Forge asUser issue verifier, dedicated embeddedIncident resolver and issue-context Custom UI resource are now implemented locally. The local manifest adds static jira:issueContext/resource/function only; no new scopes, external egress, SQL migration or hosted registration. A separate scoped Vite entry builds dist/issue-ui and leaves the global page entry intact. UI sends only action:read; current state/readiness and immutable creation/SLA snapshots are distinct, with explicit load/retry and no automatic data polling or mutation controls.

The boundary requires DEVELOPMENT, server account/issue/project context, extension type jira:issueContext and a finite compatibility list of the exact own UI key or dedicated function key. This is a provisional compatibility policy because official moduleKey semantics remain unverified; no wildcard/browser-key fallback. Exact deployed native context shape, module-key identity, host theme/layout and actual permission/tenant denial remain acceptance gates. Independent asUser issue/project permission and fresh SQL tenant grants carry the data-authorisation decision.

The extra /myself lookup was removed after security review identified its missing read:jira-user scope. Resolver account identity and interactive asUser are used without impersonation/app fallback or expanding permission. Unsupported shape/permission/configuration fails closed. A positive GET supplies Browse/issue security visibility, not permission to mutate Jira or bypass Light House workflow. Operational SLA is explicitly unverified when mutable state cannot be read; snapshot deadlines remain visible.
