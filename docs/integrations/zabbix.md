# Zabbix integration contract — planned Sprint 2

Primary source is Zabbix. The current official manual resolves to 8.0 on 2026-11-24; record the actual tested media type/server version before claiming compatibility. [Webhook media](https://www.zabbix.com/documentation/current/en/manual/config/notifications/media/webhook) and [HttpRequest objects](https://www.zabbix.com/documentation/current/en/manual/config/items/preprocessing/javascript/javascript_objects) support script-driven HTTPS/header delivery.

Proposed payload schema v1: stable `externalEventId`, `problemEventId`, `kind` (problem/recovery/update), `externalResourceId`, UTC `occurredAt`, source severity and bounded title. Source/tenant identity is derived from bearer credential configuration, not supplied payload fields. A recovery must preserve the original problem link. Map the exact problem/recovery macros and timestamp representation on the pinned Zabbix version in Sprint 2; the JSON field names here are Light House's contract, not claimed native Zabbix JSON fields.

The handler authenticates headers, enforces a 64 KiB application body cap, validates unknown input, calls MonitoringAdapter and durably records an inbox row before queue dispatch/acceptance. Use a generic receipt response; no customer/context data in responses. Ack semantics and retryable 429/503 responses must be tested against Zabbix media retry configuration. Never acknowledge a receipt that is not durable.

The adapter normalises monitoring semantics only; enrichment/SLA/Jira work belongs in application services. Duplicate IDs, problem repeats, out-of-order recovery, unknown hosts, bad JSON, rotated credentials and caller tenant spoofing are contract gates. Prometheus/LibreNMS may later implement the same port without source-specific branches in orchestration. No adapter/webhook endpoint exists yet. A fixture transport is explicitly labelled and uses the same future authenticated ingress as real Zabbix; it cannot prove live source connectivity.
