# Zabbix integration contract — planned Sprint 2

Primary source is Zabbix. The current official manual resolves to 8.0 on 2026-11-24; record the actual tested media type/server version before claiming compatibility. [Webhook media](https://www.zabbix.com/documentation/current/en/manual/config/notifications/media/webhook) and [HttpRequest objects](https://www.zabbix.com/documentation/current/en/manual/config/items/preprocessing/javascript/javascript_objects) support script-driven HTTPS/header delivery.

Proposed payload schema v1: stable `externalEventId`, `problemEventId`, `kind` (problem/recovery/update), `externalResourceId`, UTC `occurredAt`, source severity and bounded title. Source/tenant identity is derived from bearer credential configuration, not supplied payload fields. A recovery must preserve the original problem link. Map the exact problem/recovery macros and timestamp representation on the pinned Zabbix version in Sprint 2; the JSON field names here are Light House's contract, not claimed native Zabbix JSON fields.

The handler authenticates headers, enforces a 64 KiB application body cap, validates unknown input, calls MonitoringAdapter and durably records an inbox row before queue dispatch/acceptance. Use a generic receipt response; no customer/context data in responses. Ack semantics and retryable 429/503 responses must be tested against Zabbix media retry configuration. Never acknowledge a receipt that is not durable.

The adapter normalises monitoring semantics only; enrichment/SLA/Jira work belongs in application services. Duplicate IDs, problem repeats, out-of-order recovery, unknown hosts, bad JSON, rotated credentials and caller tenant spoofing are contract gates. Prometheus/LibreNMS may later implement the same port without source-specific branches in orchestration. A local adapter/intake service now exists on the isolated Sprint2 branch; no webhook endpoint is registered or deployed. A fixture transport is explicitly labelled and uses the same future authenticated ingress as real Zabbix; it cannot prove live source connectivity.

Sprint 0.5 intake boundary: automated Border Control validates security/payload/replay before normalisation. Legitimate valid events with missing inventory/customer mappings retain a durable visible NOC manual-triage receipt and original time; never silently discard them. A recovery signal updates evidence only; operational restoration validation and guarded JSM closure remain domain responsibilities.

## Local implementation status — 2026-11-27

Payload v1 now strictly includes schemaVersion plus the seven fields above; externalEventId/problemEventId are positive decimal strings (up to32 digits), severity is a string0–5 and title is bounded200 characters. Problem events require matching event/problem IDs; recovery retains the supplied original problem link. Exact Zabbix media/macros/version compatibility remains untested. Required headers: Authorization Bearer, X-Light-House-Key-Id, X-Light-House-Sent-At and application/json content type. This describes a local contract, not a live URL or source setup instruction. See ADR-0018 and Sprint2 report for proposed defaults and remaining runtime/UI/transport work.

## Current local LH-103 contract — 2026-11-27

The adapter/intake/consumer/UI are now locally wired and built, with a v2 static webtrigger in manifest; no endpoint has been generated or deployed. Source/tenant authority comes from encrypted credential bindings and trusted runtime context. Native Zabbix server/media version remains untested;8.0 docs are a reference, not a compatibility claim. A source integration must send original decimal event/problem IDs, UTC occurrence and string severity0–5, preserve problem linkage for recovery, and retry only429/503 with bounded backoff while preserving identical normalized event content. Request sent-at must be current on retries; original occurredAt must not change. Changed content for the same event/kind conflicts. Unsupported/unknown keys (including caller tenant/source) reject.
