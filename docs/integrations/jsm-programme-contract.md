## Creation, reconciliation and tenancy

Call only with a trusted installation/tenant context derived by the Forge boundary, never a client-selected context. Repository incident/configuration/intents must match both boundaries. Configuration changes require a stored active tenant administrator and Jira administrative checks through the injected authorisation port, an Atlassian-user context, expected-version CAS, and server-side verification of desk/project/request-field metadata. A monitoring-source/system actor cannot configure it.

Project, service desk, request type and priority IDs are explicit positive decimal configuration strings. Four distinct custom fields hold a searchable reconciliation marker, warning datetime, operational deadline datetime and policy-version UUID. Configuration rejects arbitrary field syntax and mismatched tenant/installation. Metadata verification requires all supplied fields, expected schemas and no additional unsatisfied required field. Summary/description/marker/policy require non-enumerated string fields; warning/deadline require datetime fields and priority uses the configured priority ID. Hidden/custom field availability still requires native verification on the target request type. No arbitrary field bag or real account/reporter/participant is accepted by the application contract.

Initial request values contain a bounded synthetic summary/description, selected priority, immutable warning/deadline/policy and `light-house-<internally-generated-intent-uuid>` marker. Marker is embedded in the first POST, not a subsequent update. Incident customer/contact lists, original payloads and credentials must never be passed into these fields. Configuration is verified again before each permitted create to detect target/field drift; failed verification persists a configuration blocker rather than posting. Remote configuration can still change between reads and writes; target-site permissions and guarded configuration remain native acceptance requirements.

`ensure` atomically inserts-or-reads one intent per installation/tenant/incident, preserving its original request/config snapshot. `claim` compares version, verifies no active lease or future due time, increments the selected attempt counter and records a lease token/state before any external call. Create claims allow prepared/retry_wait with attempts below3; reconcile claims allow ambiguous/expired sending/reconciling or exhausted retry_wait, with reconciliation count below3. A new call during an unexpired lease is pending. After a crash, the expired sending state reconciles rather than repeating the POST.

`settle` atomically saves mapped identity, state and audit under the same installation/tenant/id/token. Mapping has unique installation/issue identity so two tenant incidents cannot claim the same issue. If mapping persistence fails or stale fencing rejects completion, the service returns pending; original sending state requires reconciliation. Concrete repository implementation must satisfy these invariants; the application unit fixture alone is not evidence of SQL enforcement.

Only201 with valid ID/key and exact desk/requestType association is a confirmed creation response.400/401/403/404/422 are configuration review, not automatic retries.429 with bounded positive integer Retry-After schedules a persisted due time measured from the received response, not the worker start, and max3 create attempts; unsupported/missing/unbounded delay stops as configuration review rather than retrying early.5xx, network error, malformed success or unexpected response are ambiguous. No raw exception/body is returned or logged.

Enhanced JQL search is bounded to2 candidates, a configured numeric project and custom field plus validated marker. Each candidate requires exact returned marker/project and an independent JSM request association matching configured desk/requestType. A partial page, invalid shape, foreign/near match or inaccessible request is incomplete evidence. Duplicate returned identities are not accepted. Exactly one verified candidate on a complete result links; multiple candidates require manual review. Zero results never prove a failed create because visibility/index lag may hide it; after3 bounded reconciliation claims the operation remains manual review, never a blind create. No exactly-once claim is made.

## Integration and native prerequisites

The lead owns concrete Forge SQL implementation/migration and runtime wiring. The incident projection expected by `JsmRepository.incident` contains id, installationId, tenantId, bounded summary/description, P1/P2/P3, warningAt, deadlineAt and policyVersionId. It must originate from the stored enrichment/SLA snapshot, not editable client request values. Queue retries use the stored intent and due time. Integration must preserve operational stage/owner/SLA authority and treat monitoring recovery as evidence, never a Jira resolution instruction.

The current manifest has no JSM request scopes. Future exact-artifact review/upgrade must consider `write:servicedesk-request` for creation and customer transitions, `read:servicedesk-request` for request metadata/readback, and existing `read:jira-work` for enhanced search. `write:jira-work` is a separate future requirement only for selected Jira platform field/transition writes, not an implicit permission needed by the current JSM create endpoint. Scope presence does not grant service-desk create, Browse Projects, issue security, Transition Issues or administrator permissions. No scope was added or consent requested here.

Before native execution verify explicit synthetic project/serviceDesk/requestType/required field configuration, app create/read/search permissions, custom marker search behavior, field formats, priority mapping and protected operational fields. Test initial create, concurrent duplicates, Jira-committed/response-lost and mapping-write loss, index lag, near/multiple candidates,429 retry scheduling, configuration drift and wrong-tenant/installation denials. Do not inject native faults without separately authorised scope/budget. One HTTP success is not native notification delivery or workflow bypass prevention.

Customer transitions are available through JSM GET/POST `/rest/servicedeskapi/request/{issueIdOrKey}/transition`, with view/Transition Issues permissions and Add Comments if used. Their available customer transitions do not guarantee agent workflow coverage. Later wiring must obtain configured transition IDs and check canonical server workflow gates; no guessed transition IDs or automatic close on recovery. Native UI/REST/automation bypass prevention, ownership conflict detection and notification schemes remain required acceptance. JSM owns notifications and native SLA calendars; app deadlines do not create native SLA goals. No external email provider is introduced.
