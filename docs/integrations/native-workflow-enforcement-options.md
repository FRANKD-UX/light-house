# Native workflow enforcement options

Verified against the official sources below on 2026-11-28. Documentation research only: no workflow, field, permission, manifest, installation or hosted data was changed. Forge MCP was unavailable in this session. ADR-0015 and the existing native-transition contract remain authoritative; native closure remains disabled.

## Established capability and remaining proof

The Forge workflow-validator module is explicitly Preview. Its function mode can execute on configured transitions. This establishes a potential programmable enforcement mechanism, but does not establish a GA SQL-backed validator or a verified Light House lease protocol. Preview suitability for early production adopters is not project approval or proof of fail-closed behaviour. [Forge workflow validator](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-workflow-validator/).

There are also standard native workflow controls. Company-managed workflow documentation lists permission, group and role restrictions, field-value conditions, and grouped conditions. Consequently, “no proven GA SQL-backed validator” must not become “no native enforcement options exist.” Hide From User explicitly permits REST-triggered transitions and cannot enforce the required bypass boundary. [Configure advanced workflows](https://support.atlassian.com/jira-cloud-administration/docs/configure-advanced-issue-workflows/).

Forge custom fields offer `readOnly: true`: users cannot edit them through the UI or Edit Issue REST API; the documentation also excludes automation writes to read-only fields. The owning app can update these fields through its dedicated REST API. This provides an app-controlled Jira value, not a synchronous read of Forge SQL. Its value function runs when an issue is viewed, so it cannot be assumed to refresh approval during a transition. [Forge custom field](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-custom-field/).

Group-based workflow restrictions are documented for company-managed spaces and require administrative workflow configuration. Publishing a shared workflow can affect other spaces; any future experiment must use an isolated synthetic workflow. [Restrict workflows by group](https://support.atlassian.com/jira-cloud-administration/docs/restrict-workflows-based-on-user-groups/).

## Recommended next evidence

Prepare a small, separately authorised synthetic workflow experiment for the standard-condition/read-only-field candidate before proposing a platform exception. First verify field-type compatibility and execution identity, then document the exact workflow and scope changes. Test direct UI, REST and automation paths; another permitted actor; stale, missing, cleared and expired approval; concurrent operations; and failure between field publication, transition and cleanup. Include every alternative transition into protected states and workflow administrator changes in the threat model.

A successful field-condition experiment alone must not enable closure. The acceptance decision still needs a defensible strategy for stale approval, actor/version binding, concurrent consumption and recovery without a cross-product transaction. If that cannot be established, the next owner decision is whether to authorise a tightly scoped Preview-validator investigation or retain disabled native closure while continuing independent local functionality. No new approval is requested by this research note.

An observed target status proves a postcondition at observation time; it does not identify the causing transition or prove its exact occurrence time. Preserve that distinction in both candidate designs and acceptance evidence.
