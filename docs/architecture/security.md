# Security architecture and threat model

Design reviewed 2026-11-24; not a penetration test. The historical Sprint 0 surface was a read-only metadata resolver. Sprint 1 now adds server-authorised synthetic inventory SQL, membership/configuration and explicit development migration/seed/repair actions; see the current Sprint 1 security review. Future surface includes authenticated monitoring, tenant inventory/configuration and JSM write access. See [capability assessment](../project/forge-capability-assessment.md) for platform source URLs.

Assets: credentials, tenant boundaries, topology/customer relationships, incident integrity, SLA history, JSM permissions and billing allowance. Actors: anonymous internet caller, compromised monitoring source, malicious or mistaken ISP admin, low-privilege Atlassian user and failing upstream provider. Boundaries: public webtrigger, Forge resolver context, ISP scope within an installation, SQL/KVS, JSM project and directory/support providers.

| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |

## Proposed webhook authentication

Use a cryptographically random per-source bearer secret over HTTPS, with a public credential key ID header for bounded lookup. Forge KVS secret key encodes ISP/source/reference; SQL reference metadata binds tenant/source and validity. Compare fixed-size digests using Node crypto constant-time comparison; reject malformed lengths first. Token/ID/timestamp parsing has strict bounds. No query token or caller tenant ID is accepted as authority.

Zabbix HttpRequest supports custom headers; a webhook media script can set `Authorization: Bearer …` without assuming unavailable HMAC primitives. Do not copy documentation examples that log the whole parameter object. Store the Zabbix-side secret using supported restricted configuration and test visibility/rotation on the pinned version. HMAC signing is a possible later upgrade only after end-to-end runtime primitive support is verified; it is not a Sprint 0 capability claim. Basic auth is feasible but offers no material advantage here; IP allowlisting alone cannot establish a source identity.

Proposed rotation: add a new credential reference, activate it and update Zabbix, allow a short explicit overlap (proposed 24h), then revoke/delete old material. Credential ID changes do not change idempotency keys. Revoke immediately on compromise; admin actions create redacted audit entries. Replay age/skew and rotation duration need owner review. Timestamp/duplicate controls supplement bearer authentication and do not provide signed payload authenticity.

## Permissions and configuration

No scopes or egress are requested in Sprint 0. Introduce `storage:app` for KVS only when used; JSM/Jira read/write scopes must match each actual REST endpoint and access model. `asApp` calls from webtriggers require explicit tenant/source authority because no Atlassian user is present. Administrative UI resolvers need both trusted Atlassian identity/permission checks and app tenant roles. Do not grant broad admin scopes merely for convenience. Secrets never cross Bridge; internal errors expose a safe code/message/correlation ID only.

## Sprint 0.5 workflow threats — design only

| Threat                                             | Required control                                                                                                                         | Verification / residual risk                                                                                                                            |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged client stage/gate/actor or tenant           | Server derives identity/membership, evaluates fixed transition and checklist version; UI is never authority                              | Sprint 3/4 direct invokes, viewer/revoked user, cross-tenant incident/evidence/team tests                                                               |
| Concurrent accept/reject/return or stale checklist | Expected incident version and one active handoff pointer; validation tied to incident revision; idempotent command receipt               | Race accepts/rejects, duplicate command, changed evidence invalidates closure; partial writes repaired before new command                               |
| Ownership gap during transfer                      | Origin owns until accepted; receiver owns until accepted return; assignment history and reason required                                  | Reject/missing engineer/retired team leave original accountability intact                                                                               |
| SLA laundering through transfer                    | Immutable cycle start/deadline and handoff SLA snapshots; server-only policy selection                                                   | Multiple teams and rejected/returned handoffs preserve deadline and breach history                                                                      |
| Recovery forgery or premature native Jira closure  | Source recovery is evidence only; NOC restoration gate and site-enforced guarded close path                                              | Sprint 7 recovery alone, automation/REST/bulk/native UI bypass attempts; native enforcement remains an unverified release blocker                       |
| Evidence XSS/SSRF or cross-issue data leak         | Escape bounded text, same-tenant incident/Jira attachment authorisation, no arbitrary evidence URL fetch; internal visibility by default | Malicious HTML/URLs and inaccessible attachment tests; do not copy customer lists into public comments                                                  |
| Audit omission after partial SQL writes            | Incident carries pending command envelope, block next mutation until idempotent audit/materialisation repair                             | Fault after aggregate write/before audit insert; preserve actor, before/after revision and outcome; app audit is not independently tamper-proof storage |
| Inventory gaps hide outages                        | Authenticated valid receipts visible to NOC triage with unknown impact and original start                                                | Missing site/customer mapping does not discard incident; security-invalid inputs still rejected                                                         |

No new permissions, ingress, workflow mutations or data stores are implemented in Sprint 0.5. Native Jira guards must be proven on the authorised site; reconciliation alone cannot prevent a bypass. See event-lifecycle.md ownership matrix and dependency-security-assessment.md for residual SDK risks.

## Sprint 1 reviewed surface — 2026-11-26

The actual implementation, trust-boundary traces, scanner coverage/limitations, dependency reassessment and pre-release findings are recorded in [Sprint 1 security review](../project/sprint-1-security-review.md). Scope is read:jira-work and Forge SQL; no egress, public ingress, asApp, external identity or operational JSM writes. Account/installation identity, active grants, same-tenant references, durable mutation admission and sanitized logs/errors are enforced server-side. No live SQL or second-installation acceptance is claimed.
