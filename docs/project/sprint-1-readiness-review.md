## Database safety assessment

All fifteen immutable v001 operations are CREATE TABLE IF NOT EXISTS, no DROP/DELETE/TRUNCATE/ALTER or data cleanup. Hash f868b21682183cb04d195687aa86934e0f89b941e1d4a480878bc18fbfb94f91 is enforced by the contract test. Names/order and DDL are deterministic; future changes append migrations. Metadata creation before the runner repeats harmlessly; SDK checkpoint insertion follows each successful DDL. DDL/checkpoint partial failures can repeat CREATE safely. The SDK's internal checkpoint table is additional to the fifteen application tables. Existing incompatible same-named tables would not be repaired by IF NOT EXISTS: inspect their schema and stop on mismatch.

The consumer uses per-installation concurrency limit one, verifies development context and trusted installation, checks every completed named checkpoint before ready, and records failed readiness where possible. Three execution attempts per queued event are allowed; repeated administrator queueing is a separate explicit action and is not globally capped. No read runs migrations. Inventory remains fail-closed while schema readiness is absent/provisioning/failed. Repeated ready-schema migration temporarily marks provisioning; run it in a quiet acceptance window.

Tenant-scoped parameterised queries, composite keys/uniqueness, same-tenant active references and CAS protect normal operations. No transactions, foreign keys, session locks or application-selected database connection exist. Tenant intents ≤8192 characters and aggregate pending columns ≤4096 carry generated commands/receipts; repair conditionally clears the matching intent and blocks competing inventory writes meanwhile. Native size/collation/query-policy enforcement remains to be verified. Bootstrap requires server-side global Jira administrator status, writes a draft tenant/grant then activates it, and can resume after partial failure. Seeds run only in development as tenant admin, four records per explicit batch, 44 records/eleven batches per ISP, unique fixture keys and no rerun rewrites.

Only adapted SQLite and mocked SDKs verify retry orchestration, reference/lifecycle checks, uniqueness, stale versions, idempotence, concurrent original/replay and injected failures. Native Forge SQL policy, provisioning latency, UTF-8/collation/JSON/number handling, affectedRows, duplicate error shapes, checkpoint/queue retry timing, actual simultaneous invocations and platform installation isolation remain open. No native compatibility claim is made.

DDL limit is 25 requests/minute; immediate repeated migrations/retries can exceed it despite a first attempt fitting. Avoid rapid queue clicks; back off at least 60 seconds after DDL throttling, then explicitly retry within the authorised session. Three attempts do not guarantee success under rate limits.
