# Delivery roadmap — revised 2026-11-25

Internal release target: 19 December 2026; submission: **22 December 2026 at 22:00 SAST (20:00 UTC)**. Sprints are ordered slices, not full weeks. Capacity is a high schedule risk; owner must re-estimate each exit. No Sprint 1 implementation has begun or is authorised automatically.

| Sprint | Outcome                                                                               | Exit gate                                                                                                                                                    |
| ------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0      | Engineering foundation                                                                | Local scaffold/contracts/tests/docs; external acceptance separate                                                                                            |
| 0.5    | Stabilisation and operational architecture alignment                                  | Gap analysis/ADR/ERD/ownership/security assessment/local gates; registration/runtime/remote blockers explicitly retained                                     |
| 1      | ISP tenancy, network inventory and persistence                                        | Tenant/membership/inventory/service identity migrations, manual team references, parameterisation and real SQL isolation/repair tests; no full future schema |
| 2      | Zabbix integration, monitoring adapters and automated Border Control                  | Authenticated bounded intake, replay/dedupe, normalisation, inbox/dispatch and visible manual triage for unknown mappings                                    |
| 3      | Incident enrichment, customer impact, SLA policy engine and operational state machine | Versioned impact, P1/P2/P3 deadlines/warnings, fixed graph with explicit ownership and server-side guards                                                    |
| 4      | JSM integration, guarded transitions and basic departmental handoffs                  | Real issue/notifications, request/accept/reject/return, continuous SLA/audit and site-native transition restriction evidence                                 |
| 5      | Operational dashboard, incident drawer and Jira embedded context                      | Command centre/board/shared detail workspace, honest ownership/gates/deadlines and tenant-isolated issue context                                             |

| 9      | Demonstration and submission                                                          | Working labelled synthetic demo/video, judge instructions and owner submission before deadline                                                               |

Critical path: LH-013 registration/runtime and LH-014 security disposition → LH-101 tenancy/persistence → LH-102 inventory → LH-103 authenticated intake → LH-104 enrichment/SLA/state machine → LH-105 JSM/basic handoffs → LH-106 operational UI → LH-108 recovery/closure/hardening → LH-109 regression/release → LH-110 submission. LH-107 identity/team administration remains planned and required; consent can proceed once contracts/authority exist. Basic manual team/engineer configuration supports Sprint 4 before full Sprint 6 UI. Native Jira guarded-close enforcement must be resolved before claiming the workflow complete.

Mandatory MVP retains Zabbix/shared adapter design, synthetic multi-site services/inventory, unknown-context triage, distinct impact, versioned configurable P1/P2/P3 deadlines/warnings, real JSM incidents/native notifications, NOC acknowledgement/triage, direct NOC remediation, basic accepted/rejected/returned handoffs, final validation/guarded closure, audit and operational UI, Entra/Google/manual identity mapping and fresh judge installation. Any integration scope reduction requires an explicit owner decision; provider delay is not silent completion.

Outside critical path: Zoho Desk post-resolution (LH-190), advanced workflow customisation/checklist authoring and extra SLA timers (LH-191), topology correlation, arbitrary dependency graphs, sophisticated failover, business-hour calendars, large directory sync and high-volume tuning. No general-purpose workflow designer or BPMN engine. Slice the MVP narrowly within these requirements instead of adding optional engines.
