## Failure path and reviewed SQL

`static/app/src/Inventory.tsx` requests action list with the selected tenant, allowlisted kind, empty initial cursor and limit 20. `src/forge/inventory/boundary.ts` generates a UUID, derives account identity and installation/environment from trusted runtime, then dispatches `InventoryService.list`.

`InventoryService.context` validates the tenant UUID, reads installation/environment readiness, then checks active membership against the trusted account, installation, active ISP and expiry. Client selection alone grants no access. A missing/failed readiness read becomes NOT_READY; missing membership becomes DENIED. A thrown membership SDK exception reaches the outer catch. Prior overview membership display uses a different SELECT and does not prove this membership query succeeds.

`InventoryService.list` validates the kind, cursor and integer page size 1–50, then requests one extra row. `SqlInventoryRepository.list` sends:

```sql
SELECT * FROM <allowlisted-kind>
WHERE tenant_id = ? AND id > ? ORDER BY id LIMIT ?
```

The initial binding vector is `[trustedTenantId, '', 21]`; subsequent cursors are validated UUIDv4 strings. There is no OFFSET. SQL 4.0.11 passes the separate parameter array in JSON through prepare/bindParams/execute; the driver returns `result.rows`. Each row is decoded into explicit common metadata and fields from the kind definition. The service slices to twenty records, marks pending intent only as repair-required and returns the last visible ID as next only if the extra record exists. Tenant predicates and installation-scoped SQL are preserved; dynamic table selection originates from the fixed kind registry.

Mapping assumes an array of rows with the declared scalar fields; TypeScript generics do not validate SQL responses. An SDK rejection, malformed rows envelope or decoding exception can therefore reach the same catch. A successful empty SELECT would return rows [] and next null, not UNAVAILABLE. No mutation is reachable from list. The existing service/contract tests cover page boundaries, tenant isolation and separate bindings on adapted SQLite; they do not establish Forge SQL compatibility.

The outer catch logs only event/correlation/outcome and returns `{ok:false, code, correlationId}`. An InventoryError preserves its code; every other thrown value becomes UNAVAILABLE. No explicit UNAVAILABLE originates inside service.list or repository.list. In this path an unexpected readiness/membership/list/mapping/runtime exception can be indistinguishable, subject to the readiness catch described above. New mock-SDK regression cases reproduce membership versus inventory SELECT exceptions yielding the exact same public response and log shape without writes or raw error leakage. They demonstrate attribution ambiguity, not the native exception.

Resolver 2.0.2 JSON-roundtrips the returned object after the boundary callback completes. The delivered handled UNAVAILABLE envelope demonstrates that serialization/delivery of that failure worked. A serialization exception after a successful boundary return would reject the invocation rather than generate this handled envelope. SQL 4.0.11 already JSON-decodes its response; no bigint/date conversion defect has been observed here.
